# 工作流練習：用 mattpocock/skills 跑一個小專案

> 這份文件給「我」和「這個 session 的 agent」一起看。
> 目的不只是做出專案，而是**學會該產出哪些文件、以及怎麼把工作拆開讓多個 agent 並行**。

## 0. 背景與目標

- 我的現況：有想法會先寫文件，但不確定該產出哪些文件；也不確定實作時哪些部分能拆開並行。
- 這次的做法：用 [mattpocock/skills](https://github.com/mattpocock/skills)（1.3.x）的主流程跑一次，把它的產出當作範本。
- 優先順序：**用較短的時間做較多的事**，所以能並行就並行。
- 下一個專案：改用自己的工作流，拿這次的產出對照。

**給 agent 的說明**：每個階段結束時請停下來，讓我檢查產出後再繼續。回覆一律用繁體中文。

## 2. 主流程

```text
/setup-matt-pocock-skills   一次性設定
        ↓
/grill-with-docs            釐清需求，建立 GLOSSARY.md / ADR
        ↓
/to-spec                    產出 spec
        ↓
/to-tickets                 拆成 tickets，標出依賴關係
        ↓
/implement-spec             照依賴關係並行實作，最後 code-review
        ↓
/retro                      檢討 agent 的工作環境
```

### 步驟 0：安裝與設定

```bash
claude plugin install mattpocock-skills@claude-plugins-official
```

在專案資料夾裡跑 `/setup-matt-pocock-skills`：
- issue tracker 選**本地檔案**（不用設定 GitHub，tickets 直接存成檔案方便查看）
- 文件存放位置：`docs/`

### 步驟 1：`/grill-with-docs`
- 把專案想法講給它聽，**認真回答每個問題**。這一步的品質決定後面所有步驟。
- 技術選型（語言、框架、資料庫、平台）**我自己決定**，不要讓 agent 猜。
- 明確講出「**不做的事**」，避免 agent 自作主張加功能。

✅ 檢查點：看產出的 `GLOSSARY.md`、ADR，名詞定義符不符合我的理解？

### 步驟 2：`/to-spec`
✅ 檢查點：
- spec 有哪些段落？哪些是我原本不會寫的？
- 有沒有寫清楚**模組邊界和介面（契約）**？這決定之後能不能並行。
- 如果有美術需求，有沒有一併寫出**素材規格**（見第 5 節）？

### 步驟 3：`/to-tickets`
✅ 檢查點（**最重要的學習點**）：
- 每張 ticket 有沒有寫：目標、範圍（哪些檔案）、依賴、驗收條件？
- 把依賴關係畫成圖，標出哪些可以並行（見第 4 節的判斷標準）。
- 找出**熱點檔案**（大家都會改的檔案），確認只由一張 ticket 負責。
- 如果 tickets 不到 4 張，可能找不到可以並行的部分，考慮擴大範圍。

### 步驟 4：`/implement-spec`
觀察：
- 第一批派出了幾個 subagent？為什麼是那幾張？
- 合併時有沒有衝突？衝突發生在哪個檔案？
- 最後的 code-review 抓到什麼問題？

✅ 檢查點：實際跑一次程式、看測試結果，不要只看 agent 說「完成了」。

### 步驟 5：`/retro`
✅ 檢查點：它建議改善什麼？哪些我要採納？

## 3. 文件清單參考

| 文件 | 回答的問題 | 小專案需要嗎 |
|---|---|---|
| 需求簡述 | 解決什麼問題、給誰用、怎樣算成功、**不做什麼** | 必要 |
| 設計 / Spec | 架構、模組劃分、**介面 / 契約**、資料模型、技術選型 | 必要 |
| Tickets | 拆成哪些工作、誰等誰 | 必要 |
| AGENTS.md | 安裝 / 測試指令、文件在哪裡（越短越好） | 必要 |
| ADR | 為什麼選 A 不選 B | 遇到重大決策時 |
| GLOSSARY.md | 專案專有名詞的意思 | 專案變大時 |

Ticket 範本：

```markdown
### T3：登入 API
- 目標：使用者可以用 email + 密碼登入
- 範圍：src/auth/ 底下（不要改 routes.ts）
- 依賴：T1（資料庫 schema）
- 驗收：正確密碼回傳 token；錯誤回 401
```

## 4. 並行判斷標準

### 三個條件都成立才能並行
1. **不改同一批檔案**
2. **不需要對方的產出**
3. **介面已經定好**

### 標準節奏

```text
骨架（一個 agent） → 定契約（一個 agent） → 各自實作（多個 agent 並行） → 整合 + review（一個 agent）
```

### 熱點檔案（事先指定只由一人改，或在骨架階段寫好）
- 路由註冊表（`routes.ts`、`urls.py`）
- 資料庫 schema、migration
- 共用型別、設定檔
- `package.json` / `pyproject.toml`

### 不適合並行的情況
- 專案剛開始、結構未定
- 設計還不清楚，邊做邊想
- 都在改同一個核心模組

## 5. 美術交給 Codex CLI

我會讓 Claude 透過 Codex CLI 產生美術素材（`codex-imagegen` skill，用 ChatGPT 的圖像模型）。分工如下：

| 誰做 | 做什麼 |
|---|---|
| Claude | 規劃、程式、tickets、整合 |
| Codex CLI | 圖片、icon、sprite、貼圖等美術素材 |

### 美術是天然的並行軌道
美術素材和程式碼不會改到同一批檔案，非常適合並行：

```text
定契約時一併定好「素材規格」
        ├─ 程式 tickets（Claude subagents）：先用佔位圖開發
        └─ 美術 tickets（Codex）：照規格產圖
                ↓
        整合：把佔位圖換成正式素材
```

### Spec 階段要多寫一份「素材規格」（這就是美術的契約）
- **風格指南**：畫風、色調、參考圖，確保每張圖風格一致
- **尺寸與格式**：例如 `64x64 PNG、透明背景`
- **命名規則與存放位置**：例如 `assets/sprites/player_idle.png`
- **素材清單**：列出每一張需要的圖

程式端只要照「檔名 + 尺寸」寫，就不用等美術完成。

### 美術 ticket 的寫法
`implement-spec` 預設每張 ticket 都用 `tdd`，但美術不適合 TDD，所以要在 ticket 裡寫清楚：

```markdown
### A2：玩家角色 sprite
- 類型：美術（用 codex-imagegen 產生，不走 tdd）
- 規格：64x64 PNG、透明背景、依 docs/art-style.md
- 輸出：assets/sprites/player_idle.png、player_run_1..4.png
- 依賴：無（只依賴素材規格）
- 驗收：尺寸與檔名正確；我目視確認風格一致
```

### 注意事項
- **驗收需要人看**：圖好不好看沒辦法自動測試，美術 ticket 要留給我目視確認。
- **額度分開算**：Codex 用的是 ChatGPT 的額度，和 Claude 的額度分開，並行產圖不會吃 Claude 的額度。
- **風格一致性**：一次產多張圖時，每次都附上風格指南和已完成的參考圖。
- **`/retro` 時順便檢討**：哪些美術需求描述不清，導致要重產？

## 6. 成本與效率備註

- 做同樣的量，**並行和依序的 token 總量差不多**，並行只是更快。
- 並行額外的開銷：合併衝突、各 subagent 重複讀同一批程式碼。
- 訂閱方案的額度按時間區間計算，並行只是比較早用完、等恢復，不會讓總量變少。
- 事先把常用指令（測試、git）加進允許清單，避免並行時一直被權限確認打斷。
- 做完可用 `/explain-usage` 看這次 session 的 token 分佈。
